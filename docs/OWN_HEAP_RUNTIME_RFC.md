# RFC: собственный heap и альтернативный runtime

Статус: предложение к отдельному проекту. В текущий релиз не входит.

## Цель

Проверить, даст ли специализированный heap измеримое преимущество для
типичных нагрузок yasl, сохранив `mem::Resource` и возможность отката на
`libc`, `tcmalloc` и `custom` backends.

## Обязательные измерения

Каждый прототип должен сравниваться с текущими backends на одинаковых
нагрузках из `yasl/bench`: распределения 8–511 байт в 1/4/8 потоках,
создание 200 тысяч узлов и операции строк. Отчёт публикует p50/p95 latency,
throughput, число аллокаций, peak resident memory и размеры публичных объектов.

## Контракт и безопасность отката

- `allocate`, `allocate_at_least`, `resize` и `deallocate` сохраняют текущие
  требования к alignment и фактическому размеру блока.
- Освобождение блока через другой resource остаётся ошибкой контракта и
  проверяется в debug-сборке.
- Исключения, TLS, fork и завершение потока должны иметь отдельные тесты.
- Backend выбирается конфигурацией сборки; удаление существующего backend не
  допускается до появления эквивалентного fallback.

## Linux runtime на `clone/clone3`

Такой runtime требует отдельного прототипа с описанием TLS ABI, стека,
сигналов, join/detach, отмены и взаимодействия с `pthread`. Критерий готовности
— функциональный паритет с текущим `conc` API, отсутствие регрессии в TSan и
измеримое преимущество на репрезентативной нагрузке. До этого системный
thread backend остаётся основным.

## Решение о PImpl

PImpl рассматривается только для нешаблонных классов, если измерения показывают
существенное сокращение времени компиляции или требуется стабильный ABI. Перед
изменением фиксируются `sizeof`, alignment, symbol set и время сборки внешнего
потребителя. Контейнеры, строки, atomics и vocabulary-типы в PImpl не переводятся.
